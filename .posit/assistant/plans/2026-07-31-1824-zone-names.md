# Plan: Rename `zone` values from French to English

## Problem

The `zone` column ships with six French-language values (`Afrique`,
`Ameriques`, `Asie-Pacifique`, `EEAC`, `MENA`, `UE Balkans`) inherited
verbatim from RSF's raw exports. Every other column in `rwb_standardized`
(`country_en`, `iso`, `score`, `rank`, dimension names, etc.) is English, so
`zone` is the odd one out. This is a real **data value** change (not just a
label used in one vignette), so it needs to flow through the standardization
pipeline the same way country-name consolidation already does.

## Proposed English names -- APPROVED

| Current (French) | Approved English |
|---|---|
| `Afrique` | **Africa** |
| `Ameriques` | **Americas** |
| `Asie-Pacifique` | **Asia-Pacific** |
| `EEAC` | **Eastern Europe & Central Asia** |
| `MENA` | **Middle East & North Africa** |
| `UE Balkans` | **EU & Balkans** |

### Legend/chart width check

Two labels are noticeably longer than the rest ("Eastern Europe & Central
Asia" ~29 chars, "Middle East & North Africa" ~26 chars, vs. "Africa" at 6
chars). This won't cause errors or truncation -- ggplot2 legends reserve
whatever horizontal space the longest label needs rather than clipping text
-- but it will widen the legend box and correspondingly narrow the plot
panel within the vignette's fixed `fig.width = 7`. Given 7 zone-style
entries total (6 zones + "Global mean"), the legend stays single-column by
default, so this should be a modest cosmetic tightening, not a broken
layout.

Rather than assume this from first principles, I'll render the actual
`zones_chart` chunk with the new long labels as the first implementation
step (before touching any other file) and visually confirm it looks fine.
If the legend feels cramped, low-risk fallback options (not yet applied,
only if needed):
- `theme(legend.position = "bottom")` with `guides(color = guide_legend(nrow = 2))`
- Wrapping legend labels with `scales::label_wrap(15)`

I'll only reach for one of these if the plain render looks genuinely
crowded; otherwise the long names proceed as approved with no extra
styling.

## Implementation steps

1. **Add a zone mapping file**, `inst/extdata/zone_mapping.csv` (old_name,
   new_name), mirroring the existing `consolidation_mapping.csv` pattern --
   keeps the mapping data-driven and easy to extend if RSF ever adds a
   region.
2. **Apply the mapping in `R/standardize.R`**, inside
   `consolidate_and_standardize_countries()`, as a new "Step 3c" immediately
   after the existing Step 3b (2022 zone-anomaly fix) -- English renaming
   must happen after that fix, since the anomaly fix keys off the original
   French zone labels (`"Europe - Asie centrale"`, `"Maghreb - Moyen-Orient"`)
   and the zone_lookup majority-vote logic. Add a validation check right
   after the translation (see "Relationship to the non-ASCII problem"
   below) that fails loudly if any row's `zone` isn't one of the six
   approved English values.
3. **Regenerate data**: re-run `standardize_rwb_countries()` to rebuild
   `data/processed/rwb_standardized.rds`, then re-run
   `data-raw/rwb_standardized.R` to rebuild `data/rwb_standardized.rda` (the
   object users actually load via `data(rwb_standardized)`).
4. **Update `vignettes/visualizing-trends.Rmd`**: the "Regional Trends"
   section's bulleted zone glossary currently uses the French codes as
   headers (e.g. `**\`Afrique\`** -- Sub-Saharan Africa: ...`); switch each
   header to the new English label, and drop the now-redundant translation
   since the value itself is already in English (e.g.
   `**Africa** -- Sub-Saharan Africa: Angola, Benin, ...`). Chart legend
   labels update automatically since they come from the data.
5. **Update `R/data.R`** (dataset documentation) if it lists example zone
   values.
6. **Update `README.md`** if it shows example zone values in its data
   structure table or sample output.
7. **Check `NEWS.md`** (create if it doesn't exist) -- this is a
   user-visible, breaking change to shipped data values (any downstream code
   filtering `zone == "MENA"` etc. would silently stop matching), so it
   should be called out explicitly for anyone who has already built on this
   package.
8. **Re-render vignettes** (`devtools::build_vignettes()` or
   `pkgdown::build_site()`) and regenerate `man/*.Rd` /
   `doc/*.html` so generated docs reflect the new values, not stale French
   ones.
9. **Update `AGENTS.md`** to record this as a new standardization step
   (same pattern as the existing "Phase D: Standardization" and "zone
   ASCII-normalization" entries), so future sessions know `zone` is English
   and where the mapping lives.

No changes needed in `R/clean.R`, `R/column_mappings.R`, `R/combine.R`,
`R/utils.R`, `R/update.R`, or `tests/testthat/test-clean.R` -- these all
treat `zone` generically (by column name, not by its French values) or use a
placeholder value (`"Europe"`) in mocks.

## Relationship to the non-ASCII problem

This plan is separate from the "Non-ASCII Prevention Infrastructure v2" git
hook (which only scans `*.R`/`*.Rmd`/etc. source files, not data), but it
does directly address the recurring **`zone` mojibake bug** (the
"AmA(c)riques" issue found via Q4 in the vignette work). `R/standardize.R`
already runs `repair_and_asciify()` generically on `zone` today, but that
approach is detection-based: it pattern-matches a known corruption
signature and repairs what it recognizes, so a future RSF export with a
corruption pattern the heuristic doesn't recognize could still slip
through silently, as the original bug once did.

Translating `zone` to English removes the underlying cause rather than
continuing to detect-and-repair it: none of the six approved English values
contain a diacritic, so once translated there is nothing left for an
encoding glitch to corrupt. This also enables a cheap, categorical
safeguard that the current repair-only approach doesn't offer: after the
Step 3c translation, add a hard validation check (e.g.
`stopifnot(all(result$zone %in% approved_zone_values))` or a
`cli::cli_abort()` with a clear message) that fails the pipeline loudly if
any unexpected zone value ever appears, rather than requiring someone to
notice it by eye in `glimpse()` output later. I'll add this as an explicit
sub-step of Step 3c during implementation.
